# 2026-11-05: bug #39 in detail, the weight-set guard, and upstream

#39 was found and fixed on 2026-11-04 (`9b9b19d`, `2026-11-04_rowO_bug17_bug37.md` section 3): one input channel with
two or more weight passes, the second filter group computed with the first group's weights; cause and fix in Python
(`LayerParameters.wght_transmissions_pe`). Open questions answered here: when exactly it strikes, why the RTL produced
the first group's weights instead of garbage or the bias, whether the RTL itself is wrong, and what is left.
Sections 1-6: the investigation (no change). Section 7: direction 1 applied (approved): the Python guard. Section 8:
the same check on upstream's Python.
Scripts: `2026-11-04_bug39/` (`grid39.py`, `upgrid39.py`, `probe39.py` with `B39_WDATA` / `B39_ZERO_FILTERS`, `run39.py` with
`K` / `CR` / `GLBP` / `GLBW` / `QA`). Experiments on the Python of the old formula and of a tentative #39b fix ran in
scratch worktrees; the repository code is unchanged.

## 1. The contract between toolchain and RTL

For a conv layer the host streams all weights of the layer into the weight staging buffer (`GET_WGHT`), the RTL then
runs `needed_wght_cycles` weight passes per channel batch (`iact_channel_max_cycles` = `iact_transmissions_pe`
batches) and reads `wghts_per_pe` buffer rows per pass from `wght_buffer_rd_addr`, rewinding to 0 after the last pass.
Nothing in the RTL knows how many rows the host wrote. The stream is right only if

    weight sets in the stream (needed_wght_transmissions) == needed_wght_cycles x iact_transmissions_pe

(`grid39.py` checks this; it held in every configuration that passes the regression). #39 broke it in Python.

## 2. When #39 strikes (formula before the fix)

`grid39.py`: one-layer convs, stride 1, images 8 x 4 and 28 x 28, 1 ... 64 input channels, 4 ... 128 filters, on the
16 platforms of Table 3 (CLUSTER_ROWS 1/2/4/8 x NUM_GLB_PSUM 2/4 x NUM_GLB_WGHT 3/4), 2,880 configurations per kernel.

| Kernel | buildable | old formula wrong | of which branch "more than 16 filters" (#39) | current formula wrong (#39b, section 5) |
|---|---:|---:|---|---:|
| 3 x 3 | 2,880 | 178 | 112, **all with one input channel** | 66 (3 channels) |
| 1 x 1 | 2,880 | 718 | 578 (1 ... 64 channels) | 140 |
| 5 x 5 | 2,160 | 48 | 48, one channel | 0 |
| 7 x 7 | 1,800 | 655 | 20, one channel | 635 |

For the 3 x 3 kernels the rule is exact: **one input channel and more than 16 filters per calculation**, i.e.
`filters > 16 x kernels_per_calc` (the weights fit the PE, each PE keeps 16 psums, so 2+ weight passes). The old formula
`ceil(channels / channel_div_trans)` counts channel batches: 1 for one channel whatever the filter count, right by
coincidence for 2 channels (in that branch always 2 passes) and for 4 or more channels. `kernels_per_calc` grows when
the image is narrow and clusters are free, so the threshold depends on image and platform (smallest wrong filter count,
one channel):

| Image | CR 1 (all X, Y) | CR 2 X 2 | CR 2 X 4 | CR 4 X 2 | CR 4 X 4 | CR 8 X 2 | CR 8 X 4 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 8 x 4 | 24 | 24 | 48 | 48 | 96 | 96 | never (<= 128) |
| 28 x 28 | 24 | 24 | 24 | 24 | 24 | 24 | 48 |

So MNIST Conv1 (28 x 28 x 1 -> 32) is affected on every platform except CR 8 X 4; the paper network's layer 0
(28 x 28 x 1 -> 16) never (one filter group).

**Did it ever corrupt a result?** No committed result: until 2026-10-22 one-channel MNIST Conv1 failed anyway (#17,
whose symptom covered #39), from 2026-10-22 to 2026-11-04 it was padded to two channels (the coincidence above: 2
channels, 2 passes, 2 sets), the paper network has 16 filters, and no other test had one channel with more than 16
filters per calculation. It surfaced when row O turned the padding off.

## 3. What the RTL did with the short stream (and why the first group's weights came out)

`run39.py old_n8f64 8 4 1 64 B39_WDATA=...` on the old formula (8 x 4 x 1 -> 64, 2 passes, 120 words = 24 buffer rows
in the stream): the RTL reads rows 0 ... 24 in pass 0 and rows 24 ... 48 in pass 1 (the probe of 2026-11-04), and with
the monitor of the read data **all 26 rows of pass 1 are X** (never written). With the current formula the same reads
return written rows.

* In simulation the X weights make every write condition of the PE weight path unknown, the weight SPad is not
  rewritten and keeps the first pass's weights: hence filters 16 ... 31 = kernels 0 ... 15 exactly.
* On the FPGA the unwritten URAM rows are 0 after configuration (outputs = bias) or hold the weights of an earlier
  layer or inference: wrong in a different, data-dependent way. Nothing hangs, nothing signals an error.
* The RTL computes a genuinely zero filter group correctly: `B39_ZERO_FILTERS=32:64` (filters 32 ... 63 all zero, the
  stream complete) gives the bias for them, PASS with one and with two channels. So the RTL is not wrong in what it
  computes; it trusts the host's stream length and has no check of it.

## 4. Fix of #39 (done, Python) and its effect

`wght_transmissions_pe = channel batches x filter groups` (`9b9b19d`). Only one-channel layers with more than one
weight pass change; the regression, the 12 baseline cases and Table 3 confirmed it. Cost: those layers now send all
their weight sets (e.g. 28 x 28 x 1 -> 32: 240 weight words instead of 120), still fewer than the padded two-channel
stream they replaced (MNIST Conv1 `load_wght` -240 cycles against the padding).

## 5. #39b: the same contract broken in the "tile" branch (open, no observable effect yet)

When the weights do not fit the PE (`filters x used_iact_per_PE / kernels_per_calc > Wghts_per_PE`), `LayerParameters`
tiles the filters by `wght_factor` and rounds the two halves differently:

    used_psum_per_PE = int(filters / wght_factor)                     # floor, e.g. 64 / 3 -> 21: the RTL runs ceil(64 / 21) = 4 passes
    used_wght_per_PE = ceil(filters / wght_factor) x used_iact_per_PE # ceil, 22 filters per set: the stream carries ceil(64 / 22) = 3 sets

Whenever `filters` is not a multiple of `wght_factor` the stream has fewer (and differently cut) sets than the RTL
reads. Configurations (`grid39.py`): 3 x 3 kernels with 3 input channels and 64 / 96 / 128 filters (66), 1 x 1 kernels
with 4+ channels and 128 filters (140), most tiled 7 x 7 layers (635).

Simulation: every one of them fails first for another reason, so #39b cannot be isolated today:
* 3 channels: bug #7 (the stream packs 3 bytes per pixel, the RTL moves pairs; xfail in the regression);
* 1 x 1 kernels: `run39.py K=1` hangs in the first pass already for a consistent layer (8 x 4 x 4 -> 96 at CR 1 X 2 Y 3),
  1 x 1 convolutions do not run on this RTL at all (not investigated further);
* 7 x 7 kernels: a consistent tiled layer passes (8 x 4 x 2 -> 48, 4 passes), the inconsistent 8 x 4 x 1 -> 64 fails
  64 of 64 maps, 8 x 4 x 2 -> 64 crashes the stream generation (IndexError); with a tentative fix (weights per PE and
  sets from the floored psum count, scratch worktree) the first stops at the weight encoder ("column cannot be encoded
  without an all-zero word", #22's limit) and the second still fails 64 of 64: 7 x 7 has further problems.

## 6. Directions (none applied)

1. **Python guard (recommended, no RTL):** in `LayerParameters` (or the conv mapper, next to `check_wght_buffer`), raise
   `NotImplementedError` when `needed_wght_transmissions != needed_wght_cycles x iact_transmissions_pe`. It would have
   turned #39 into an error message at stream generation, blocks #39b until it is fixed, costs nothing at run time and
   changes no stream (the equation holds in every configuration that works). Unit test over the grid of section 2.
2. **#39b fix (Python, later):** derive `used_wght_per_PE` and the set count from the floored `used_psum_per_PE`, as the
   #39 fix did for its branch; it can only be verified on the RTL once 3 channels (#7), 1 x 1 or 7 x 7 work, so it
   belongs with those fixes. Until then the guard of (1) refuses those layers.
3. **RTL diagnostic (optional, needs your approval):** remember the highest row written in `GET_WGHT` (a 13-bit
   register) and set a sticky error flag when a weight pass reads beyond it (the one-row prefetch at the end of a pass
   excepted), exposed on a status / debug output. It does not make anything compute right, it makes a host / RTL
   mismatch visible on the FPGA instead of silently wrong numbers (about 15 FF and a comparator). With (1) in place the
   toolchain cannot produce such a stream, so this is only worth it for a host other than this toolchain (a driver on
   the CPU) or for bring-up.
4. Not recommended: clearing the weight buffer per layer (cycles) or making the RTL compute the pass count itself (it
   already takes `needed_wght_cycles` from the host; the mismatch is in the host's stream, not in the RTL's loop).

## 7. Direction 1 applied: `check_wght_sets` (approved 2026-11-05, Python only)

`src/open_eye/layer_parameters.py::check_wght_sets(layer_params)` raises `NotImplementedError` ("the weight stream would
hold N weight set(s), the RTL reads P pass(es) x B channel batch(es) ...") when `needed_wght_transmissions !=
needed_wght_cycles x iact_transmissions_pe`; `ConvMapper` calls it before `check_wght_buffer` (#29) and
`check_iact_buffer` (#37). It changes no stream: where it does not raise, everything is as before. Over the grids of
section 2 it refuses exactly the configurations of the "current formula wrong" column (#39b), all of which fail
otherwise anyway (section 5). Tests (`test/test_channel_pad.py`): a short stream is refused, 30 working layers
(8 x 4 and 28 x 28, 1 / 2 / 4 / 8 / 32 channels, 16 / 32 / 64 filters) pass, the #39b layer 14 x 14 x 3 -> 64 (3 sets,
4 passes) is refused.

Verification: the full RTL regression with the check in place (189 tests of `test/cocotb_fpga`, the set of row O) gives
**185 PASS + 4 xfail, 0 FAIL**, the same as before the check: it refuses no layer of any working test. Unit tests:
369 pass (the 11 old `test_dense_output` failures unchanged). The check writes nothing into a stream, so cycle counts
and the baselines (`doc/perf/baseline_2026-11-04`, `paper_table3_2026-11-04`) and the hardware (no RTL change) stay as
they are.

## 8. Upstream's Python has the same bug

`upstream/main` moved on 2026-11-04 to `b10db82` ("Re-Enabled python interface for DW Conv", DenLeb; depthwise conv,
large edits of `layer_parameters.py`, `wght_stream_mapper.py`, the PE cluster; not reviewed beyond this question). In
the branch "more than N filters per calculation" it raises N from 16 to 32 (`used_psum_per_PE = 32`) but keeps
`wght_transmissions_pe = ceil(channels / channel_div_trans)`; the tiled branch is unchanged.

`upgrid39.py` (the check of `grid39.py` with each tree's own `LayerParameters`, 3 x 3 kernels, same grid):

* `b10db82`: the 32-psum change moves the threshold (MNIST Conv1 is no longer affected), the formula is still the
  old one and the static check finds #39 for more than 32 filters per calculation; those cases fail in simulation.
  With the formula fixed they hang instead, while two channels with two 32-psum passes work. Investigated later the
  same day (`2026-11-05_b10db82_hang.md`): not one channel, but a last weight pass that is not full; upstream's
  mapper writes the padding filters as zero words the RTL cannot decode (bug #22, fixed in the fork), and the output
  word count is wrong for such layers in the fork too (new bug #40).
* #39b (tiled branch) is in every upstream version.
