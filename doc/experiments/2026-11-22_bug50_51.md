## 1. #51: conv with several kernel groups at `CLUSTER_COLUMNS = 1` (RTL, 3 lines)

**Bug.** In the conv path of the iact converter (`OpenEye_FPGA.v`, `CONVERT_IACT` parameter FSM), when a row sweep ended,
`iact_converter_x` went back to 0, except that a branch from upstream `83a47b6` (2026-09-11) set it to
`iact_x_per_cluster` when `iact_converter_x + iact_x_per_cluster >= iact_x_add_up`, `kernels_per_calc != 1` and
`iact_x_per_cluster < iact_x_add_up`. At 2 cluster columns the sweep steps two tiles, so the first and the last condition
are never true together (scan of 8,208 layers: 0). At 1 cluster column the first is always true at a row end, so with
several kernel groups (CR 4 / 8, `NUM_GLB_PSUM` 4; 1,104 of 8,208 layers) every kernel group after the first started at
the second tile: half of the feature maps wrong (4 of 8, 8 of 16). Upstream `12340ab` removed the branch.

**Fix.** The branch removed (`iact_converter_x <= 0` for every kernel group), with a comment. No Python change.
`_run_conv_const` got a `cluster_columns` argument (default 2) for the new suite `test/cocotb_fpga/test_cluster_columns1.py`
(6 tests: 3 layers at CR 4 and 1 at CR 8 that the branch broke, 2 at CR 2 that it never touched), added to `regression.sh`.

| Layer (CC 1, `NUM_GLB_PSUM` 4, sparse) | before (2026-11-21, `dev`) | after |
|---|---|---|
| CR 4, 4 × 4 × 4 → 8 | FAIL, 4 of 8 maps | PASS |
| CR 4, 6 × 2 × 1 → 16 | FAIL, 8 of 16 maps | PASS |
| CR 4, 4 × 8 × 16 → 8 | FAIL, 4 of 8 maps | PASS |

## 2. #50: Dense with 4096 or more inputs (Python check; morning version, replaced by section 6)

**Bug** (the cause in this paragraph is wrong, section 4: it is the 12-bit `iact_x_add_up` field). `CONVERT_IACT` counts the activations of a fully connected layer in `current_x` (`reg signed [11:0]`, +2 per
buffer word, compared unsigned with `fc_size_reg`). It wraps at 4096 and every output of the layer is wrong, with no
message. Measured (Dense K → 10, sparse, seed 1):

| K | CR 2 | CR 1 | CR 4 |
|---:|---|---|---|
| 4000, 4088 | PASS | | |
| 4094 | PASS | PASS | |
| 4095 | PASS | | |
| 4096 | FAIL 10 / 10 | FAIL 10 / 10 | FAIL 10 / 10 |
| 4200 | FAIL 10 / 10 | | |

The input source does not matter: Conv 8 × 8 × 4 → 64, flatten, Dense 4096 → 10 (input written back on chip) has a right
iact buffer after the conv and 10 / 10 wrong outputs; the same with 32 filters (2048 inputs) passes. `CONVERT_IACT` runs
for every layer, not only for input from the host. (The 12-bit `iact_size_c` also overflows from K 4033 on, but `dev`'s
constructor does not read `fc_storage_valid`, so it does not matter.)

**Fix (guard, as proposed).** `layer_parameters.check_dense_input` (`DENSE_INPUT_LIMIT = 4096`), called by `DenseMapper`
with the buffer checks: refuses a Dense layer with 4096 or more inputs (`NotImplementedError`, or only a warning with
`OPENEYE_ALLOW_UNSUPPORTED=1` to reproduce the bug). In the testbench flow Dense 4096 → 10 now stops at stream
generation with the #50 message. Unit tests: `test_model_guards.py` +7 (K 3136 / 4094 / 4095 accepted, 4096 / 4200
refused, the warning mode; Dense after a flatten of 8 × 8 × 32 accepted, 8 × 8 × 64 refused). The capability itself
(larger FC inputs) needs `current_x` wider, an RTL change left for later (with `fc_size_reg` at 20 bits as upstream).
No model of the fork has a Dense input of 4096 or more (largest 3136).

## 4. Widening `current_x` (afternoon of 2026-11-22): not the cause of #50

**Upstream.** On every upstream branch that has it, `current_x` is `reg signed [11:0]`: 8 bits when it appeared
(`fe2f5ed`, 2026-08-20), 12 bits since `f7e9dde` (2026-09-03, "Fixed all errors for GateMateA1 version"), never wider;
`12340ab` widened only `fc_size_reg`. No newer upstream commit.

**Effect analysis.** `current_x` is used only in `CONVERT_IACT`: start of a row (`-padding_x`), `+1` (conv) / `+2` (FC),
`== x_bound` (conv), `>= 0` (conv; FC skips it since #19), `< fc_size_reg` / `< iact_size_x`, `+ 1 >= fc_size_reg` (odd FC
tail). Conv values are small and keep their sign, so a wider register changes nothing for conv; the Python side has no
dependency (only the debug trace `trace_convert_window` assumed 12 bits).

**Done in the working tree (not committed):** `current_x` 16 bits signed, the four comparisons with explicit zero
extension (bit-for-bit the same unsigned compares), `trace_convert_window` takes the width from the signal. Lint `fpga`
436 → 431 (0 new, 5 fixed), baseline lowered.

**But Dense 4096 → 10 still failed, with exactly the same simulated time (174,980 ns) as before.** Runs with the 16-bit
`current_x` (`wide.txt`, refusal bypassed with `OPENEYE_ALLOW_UNSUPPORTED=1`): K 4096 / 4200 / 6000 / 8190 / 8192 /
10000, CR 1, dense hardware, 4096 → 40, Conv → flatten 4096 / 8192 → Dense: all wrong; K 16382 / 16384 refused by the
weight buffer (8,208 rows > 8,192, #29).

**The real cause: `iact_x_add_up`, a 12-bit field that holds K for a Dense layer** (`layer_parameters.py:1958`,
`regmap.yaml`). In the FC write path of `iact_stream_constructor.v` (lines 579, 592) the pair counter
`x_pos_in_w_cycle` and `next_x_value_add` (pairs, at most K / 2) are compared with `iact_x_add_up`: below 4096 the
bound is never reached, at K = 4096 the field wraps to 0 and both compares fire, so the write window is reset and the
activations land in the wrong place. This explains the exact boundary (4095 right, 4096 wrong) and why the input source
does not matter.

**Experiment** (scratch worktrees, removed; `x50_experiment.txt`): the Dense mapper sends `iact_x_add_up = min(K, 4095)`.

| K → 10 (CR 2, sparse) | clamp, `current_x` 12 bit | clamp, `current_x` 16 bit |
|---:|---|---|
| 4096 | PASS 192,340 ns | PASS 192,340 ns |
| 4097 (odd) | PASS 192,340 ns | |
| 6000 | PASS 279,360 ns | PASS 279,360 ns |
| 6001 (odd) | PASS 279,390 ns | PASS 279,390 ns |
| 7000 / 7600 / 8000 / 8100 | | PASS 324,500 / 350,560 / 369,680 / 373,180 ns |
| 8180 / 8184 / 8186 / 8190 | | FAIL (the pair counter reaches the clamped bound) |
| Conv 8 × 8 × 4 → 64, flatten, Dense 4096 → 10 | | PASS |

The clamp alone fixes #50 up to K = 8100 (verified), and the width of `current_x` makes no difference at all (same ns).
Larger K would need the constructor's 12-bit FC pair path (`iact_x_add_up`, `x_pos_in_w_cycle`, `next_x_value_add`)
widened in RTL and in `regmap.yaml`; the weight buffer caps K × N anyway (K 16382 → 10 is refused).

### 6b. #50: clamp and exact limit

**Fix.** `DenseMapper` sends `iact_x_add_up = min(K, 4095)` (`layer_parameters.dense_add_up_register`) instead of K
mod 4096. Nothing changes below 4096 inputs. In the FC write path the register is only an upper bound for the pair
counters, so the clamped value behaves exactly as K as long as the counters stay below it.

**How far the counters go: a monitor in the constructor.** A scratch copy of `iact_stream_constructor.v` with a
`$fdisplay` monitor (`round2/monitor/mon50_constructor.patch`, never committed) logged, per constructor, the largest
`x_pos_in_w_cycle` and window start, the fires of the two compares with `iact_x_add_up` and the state at the end of
every write phase (`round2/monitor/*.log`). One write phase covers the whole input. Cluster row r starts at
`x_start = r · NUM_GLB_WGHT · used_iact_per_PE / 2` (18 r) and writes one window of
`used_iact_per_PE · PEs_Y / 2` = 18 pairs per pass, the windows `iact_x_pos_inc` = 18 · CR apart. When it leaves its last
window (of `diff_iact_layer`) it computes one more start, and it leaves the write phase one position later.
`layer_parameters.dense_pair_counters` gives these values, and they match every monitored value:

| run | per cluster row: position at the end / last start computed | RTL |
|---|---|---|
| CR 2, K 4000 (56 passes) | row 0 1999 / 2016, row 1 2017 / 2034 | PASS |
| CR 4, K 4000 (28 passes) | rows 0 to 3: 1963 / 2016, 1981 / 2034, 1999 / 2052, 2017 / 2070 | PASS |
| CR 1, K 8100 (225 passes) | 4051 / 4050 | PASS |
| CR 2, K 8100 (113 passes) | 4051 / 4068, 4069 / 4086 | PASS |
| CR 2, K 8180 (114 passes) | row 0 4087 / 4104 → wraps to 8; row 1 reaches 4094 and resets (`x_pos_in_w_cycle == iact_x_add_up + 1 - 1 - 1`) | FAIL |
| CR 4, K 8100 (57 passes) | rows 0 to 2 last start 4104 / 4122 / 4140 → wrap to 8 / 26 / 44; row 3 resets at 4094 | PASS (see below) |

**Exact condition.** With the clamped bound the constructor behaves as with K if its position never reaches
4095 − 1 = 4094, where it resets: then every window start it writes from is at most 4094 − 18 − 1, so there is no window
reset (`next_x_value_add >= iact_x_add_up`) and neither the start nor start + window (`x_range_lower_bound +
iact_values_per_cluster_transmit`, a 12-bit sum) wraps. The start computed after the last window may pass the bound or
wrap, but nothing is written from it before the phase ends (CR 4 K 8100 rows 0 to 2, CR 8 K 8064). `check_dense_input`
refuses a Dense layer above 4095 inputs whose last position exceeds 4093:

| platform (CC 2) | largest K | passes × inputs per pass | position at the limit |
|---|---:|---|---:|
| CR 1 | **8172** (the weight buffer, #29, refuses 8173 → 10 too) | 227 × 36 | 4087 |
| CR 2 (default) | **8136** | 113 × 72 | 4069 |
| CR 4 | **8064** | 56 × 144 | 4033 |
| CR 8 | **8064** | 28 × 288 | 4033 |

**RTL runs** (Dense K → 10, `runs.txt`): at every limit PASS (CR 1 8172: 504,210 ns; CR 2 8136: 373,220 ns; CR 4 8064:
306,140 ns; CR 8 8064: 284,340 ns, its last start 4158 wraps), CR 8 7776 PASS, CR 2 6001 (odd) PASS (afternoon). Above the
limit: CR 2 8173 and 8180 FAIL 10 / 10, and the afternoon's 8184 / 8186 / 8190 too. **One pass above the limit can still
come out right**: CR 2 8137 and 8172, CR 4 8065 and 8100, CR 8 7777 (that one is not above the limit) PASS. The row whose
last window is broken (window start + 18 ≥ 4096, or the reset at 4094) writes that window wrong, but at these K the window
holds only the padding pairs after the input (the converter pads every pass to complete tiles), whose weights are 0. At
CR 2 that holds as long as the input ends before pair 4086, the start of row 1's last window: 8172 right, 8173 wrong,
as measured. The check does not rely on this (it would depend on the padding and on zero weights), so it gives up at
most one pass (72 inputs at CR 2) against the measured last right K.

**Unit tests** (`test_model_guards.py`): the register value (10, 4095, 4096, 8136, 20000), the limits of CR 1 / 2 / 4 / 8
(3136, 4095, 4096, 6001 and the limit accepted, limit + 1 refused, warning mode), the monitored counter values, Dense
after a flatten of 8 × 8 × 64 / 127 accepted and 8 × 8 × 128 refused. **RTL suite** `test/cocotb_fpga/test_dense_input.py`

### 6c. #7: odd input channel counts padded in Python

`channel_pad.pad_first_layer` now pads a first convolution with an odd channel count above 1 by default (no environment
variable): 3 → 4, and above 4 to the next multiple of 4 (5, 7 → 8, 9, 11 → 12), because **6 and 10 channels are wrong

### 6d. #9: the stream file check skips the slots without an output

`generic_test_utils.check_results` takes the slot positions `calculate_conv_serial` already records while it writes
`dma_stream_ref.txt` (`[filter, x, y]`, `None` for a slot without an output; `compare_stream_Conv` decodes the DUT
stream with the same list). For a convolution, `OpenEye_FPGA_tb` passes them. A line that differs only in slots without
an output is then not a difference, and their count is logged. All other bits are still compared, the unused upper bits
of the word included. Without the positions the check is the old one. Unit tests: `test/test_check_results.py`
(6: equal streams; a padding-slot difference fails the plain check and passes with the positions; a real slot, the upper
bits, a wrong position list and missing lines still fail). The xfail marks of `test_mnist_conv[conv3_7x7_c64_f64]` and
`test_trained_mnist_conv[conv3_7x7_c64_f64]` are gone. A small 7 × 7 × 4 → 8 passes as well (20,920 ns). The value check
and the independent numpy check were always right and are unchanged. The RTL still writes the idle PE's psum into the
slot, and the host must ignore it, as the decoder does.
