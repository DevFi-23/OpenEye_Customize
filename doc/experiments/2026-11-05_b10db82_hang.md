# Why upstream `b10db82` hangs once bug #39 is patched, and new bug #40 (uneven last weight pass): 2026-11-05

Investigation only: no RTL change, no change of `dev`'s Python. Upstream trees are scratch worktrees of `b10db82` and
`36395dd`; "+ fix" = the fork's #39 weight-set formula patched into the tree's `layer_parameters.py`, nothing else.
Probes: `2026-11-05_b10db82_hang/` (`b10db82_probe.patch` = the scratch edits: #39 formula, PE dump in the stall
report and a per-state trace of one PE in `rtl_test_utils.probe_fsm_states`; `up_spad.py`, `params_up.py`,
`padded_order.py`). Simulations: `2026-10-31_upstream_review/up_run.py` (upstream) and `2026-11-04_bug39/run39.py`
(`dev`), random data, seed 1, CR 2, 2 cluster columns, NUM_GLB_PSUM 4, NUM_GLB_WGHT 3.

## 1. Short answer

* The hang is **not** a one-channel problem and not a 32-psum problem: it happens exactly when the **last weight pass
  is not full** (filters per calculation not a multiple of the psums per PE), e.g. 96 = 64 + 32 filters with
  32 psums x 2 kernels per calculation, or 48 = 32 + 16. Even splits (64 + 64, 32 + 32) pass with one channel.
* Cause: upstream's weight mapper writes the weights of the padding filters (96 ... 127) as explicit zero entries.
  `data_pipeline_wght.v` reads all-zero words as stream padding and has a 4-bit zero-run field, so the PE gets a
  weight address SPad with 2 instead of 3 column pointers and its MAC loop never ends. This is the mechanism of
  **bug #22**, which the fork fixed in Python (`conv_wght_encoding.py`, 2026-10-24); upstream never did.
* Without the #39 patch `b10db82` does not hang (the stream holds one weight set) but fails every feature map:
  #39 plus a second, older problem that the fork has too, **new bug #40**: for an uneven last pass the Python counts
  the output and bias words with the real filter count while the RTL computes and sends the padded one, and the
  testbench reference uses the wrong pass count. The RTL itself computes such layers right (`dev`, section 4).

## 2. Isolating the condition

| Tree | Case | Weight passes (psums/PE x kernels per calc.) | Result |
|---|---|---|---|
| `b10db82` | 8 x 4 x 1 -> 64, 28 x 28 x 1 -> 32 | 1 (32 x 2, 32 x 1) | PASS |
| `b10db82` | 28 x 28 x 2 -> 64 | 2 (32 + 32) | PASS |
| `b10db82` | 8 x 4 x 1 -> 96 / 28 x 28 x 1 -> 48 | 2, last one half full | FAIL 96 / 96, 48 / 48 maps |
| `b10db82` + fix | 8 x 4 x 1 -> 128 / 28 x 28 x 1 -> 64 | 2 (64 + 64 / 32 + 32) | **PASS** / **PASS** |
| `b10db82` + fix | 8 x 4 x 1 -> 96 / 28 x 28 x 1 -> 48 | 2, last one half full | **hang**: no FSM progress, main state 10 (WAIT_FOR_RESULTS), psum state 2 (CALCULATE_PSUM), psum cycle 0 |
| `36395dd` + fix | 8 x 4 x 1 -> 64, 28 x 28 x 1 -> 32 | 2 (16 + 16) | PASS (2026-11-04) |
| `36395dd` + fix | 28 x 28 x 1 -> 24 / 8 x 4 x 1 -> 48 | 2 (16 + 8 / 32 + 16) | **hang** / **hang**, same signature (PEs in CALCULATING): not tied to the 32 psums of `b10db82` |

Python of `b10db82` for these layers (`params_up.py`): every one has 32 psums per PE, `used_wght_per_PE` 96, one
channel batch; the patched tree has as many weight sets as passes. One channel with an even split passes, so neither
the channel count nor the 32 psums is the condition.

## 3. The hang

Stall report (all used PEs of all four clusters): `current_state_computing` = 6 (CALCULATING), `iact_ready` 1,
no iact enable, `psum_ready_o` 0: the PEs never finish their MAC loop, so CALCULATE_PSUM waits for ever.

Per-state trace of PE (x1, y0) of cluster (0, 0) (`B40T` lines of the probe), `aw` / `dw` = word counts of the weight
address / data SPad as `data_pipeline_wght` decoded them:

| Load | 8 x 4 x 1 -> 128 (passes) | 8 x 4 x 1 -> 96 (hangs) |
|---|---|---|
| first pass | aw 3, dw 48, column pointers 16, 32, 48 | aw 3, dw 48, pointers 16, 32, 48 |
| second pass | aw 3, dw 48 (every later load the same) | **aw 2, dw 9**, pointers 16, 24; CALCULATING from 29,900 ns, never left (`wght_data_vec` 17 > `dw` - 1) |

With three iact rows and two column pointers the exit condition of CALCULATING
(`wght_data_vec >= wght_data_end` together with the iact address end) is never met.

Weight data SPad of the PEs per pass, built with `b10db82`'s own `ConvWghtStreamMapper` (`up_spad.py`, random
non-zero weights):

| Case | Pass 1 | Pass 2 |
|---|---|---|
| 8 x 4 x 1 -> 96, 28 x 28 x 1 -> 48 | 48 words, no zero entry | 48 words: **48 zero entries, 24 all-zero words, longest zero run 16** |
| 8 x 4 x 1 -> 128, 28 x 28 x 1 -> 64 | no zero entry | no zero entry |

The padding filters do not exist in DRAM, the mapper's `try/except` stores them as value 0 with overhead 0. The
format `data_pipeline_wght.v` decodes (see `src/open_eye/conv_wght_encoding.py`) cannot carry that: an all-zero word
resets the data SPad write address (it is taken as per-PE stream padding), a zero run longer than 15 does not fit
the 4-bit overhead, and the column boundaries are found by counting positions. That is exactly bug #22 (zero
weights corrupt or hang the layer), found with trained weights on 2026-10-24 and fixed in the fork by
`conv_wght_encoding.encode_columns`; upstream still has the old mapper. In the fork the same layers do not hang
(section 4).

The hang therefore needs both fixes upstream lacks: #39 (otherwise the second weight set is not in the stream at all)
and #22 (otherwise the padding zeros break the encoding).

## 4. New bug #40: uneven last weight pass (the fork has it too)

`dev` (with #39 and #22 fixed, `check_wght_sets` passes these layers):

| Case | Passes | Result |
|---|---|---|
| 28 x 28 x 1 -> 24 | 16 + 8 | FAIL 24 / 24 maps |
| 28 x 28 x 2 -> 24 | 16 + 8 | FAIL 24 / 24 |
| 8 x 4 x 1 -> 48 | 32 + 16 (16 psums x 2 kernels) | FAIL 48 / 48 |
| 28 x 28 x 1 -> 48 (control) | 16 + 16 + 16 | PASS |

The RTL is right. Decoding the DUT's words in the order of the reference generator run with the filter count padded
to passes x psums per PE x kernels per calculation (`padded_order.py`) gives, against numpy:

| Case | Padded words / words the DUT sent | Real outputs among them | Equal to numpy | Never sent |
|---|---|---|---|---|
| 28 x 28 x 1 -> 24 | 14,336 / 10,752 | 14,112 | **14,112 (0 differ)** | 4,704 of 18,816 |
| 28 x 28 x 2 -> 24 | 14,336 / 10,752 | 14,112 | **14,112** | 4,704 |
| 8 x 4 x 1 -> 48 | 1,024 / 768 | 1,152 | **1,152** | 384 of 1,536 |
| 28 x 28 x 1 -> 48 | 21,504 / 21,504 | 37,632 | 37,632 | 0 |

The fork's encoder (#22) writes the padding filters as zero-weight columns the RTL decodes, so the RTL computes and
sends `passes x psums/PE x kernels` filter slots per output position, the padding slots included. The Python disagrees
in three places, all with the real filter count:

1. `layer_parameters.py:1469` `psum_output_words = output_cycles x filters x Clusters x NUM_GLB_PSUM / 2`: the RTL
   stops reading out after that many words (`psum_pipeline.v:777`, `last_data_o`), so the last
   1 - filters / padded of the outputs never leaves the chip (a quarter for 24 = 16 + 8).
2. `layer_parameters.py:1274` `trans_cycles_psum = filters x ...`: the bias section is just as short.
3. `test_utils_main.py:574` `filter_cycles = (filters // used_psum_per_PE) // kernels`: floor (1 instead of 2), and
   line 620 moves to the next x block only when `filter >= filters`, so the reference repeats filters 0 ... 15 and
   the testbench cannot check such a layer at all.

Where (static grid of `2026-11-04_bug39/grid39.py`, 16 platforms, 2 shapes, 10 channel counts, 9 filter counts):
uneven layers that `check_wght_sets` lets through: 3 x 3 kernels 162 of 2,880 (60 in the "more than 16 filters per
calculation" branch: 1 or 2 channels with 24 / 48 / 96 filters; 102 in the tiled branch, not simulated), 1 x 1 342,
5 x 5 82, 7 x 7 135. No layer of the regression, of Table 3 of the paper or of the MNIST models is uneven (their filter
counts are multiples of the pass size), so no committed result is affected. Upstream `b10db82` has the same three
formulas (`layer_parameters.py:1311/1508`, `test_utils_main.py:542/689`; `psum_output_words` from `378a0de`,
2026-08-05).

## 5. Directions for #40 (Python only, none applied)

1. **Check** (like `check_wght_sets`): refuse a convolution whose `needed_wght_cycles x used_psum_per_PE x
   kernels_per_calculation != filters`. Small and safe; turns the silent loss on the FPGA into an error.
2. **Even split** where possible: choose the psums per PE so that the passes are full (24 -> 12 + 12, 48 with two
   kernels -> 3 x 16 or 2 x 12 x 2, 96 with 32-psum PEs -> 3 x 16 x 2): no padding slots, so also fewer MACs (the
   padding slots are computed for nothing: 25 % of the work for 24 = 16 + 8). Needs a simulation per branch that the
   RTL accepts psum counts other than 16 in the multi-pass branch; filter counts that do not divide (e.g. 40) still
   need 1 or 3.
3. **Padding in the toolchain**: count padded slots in `psum_output_words`, `trans_cycles_psum` and the bias stream,
   fix the reference / decode (`filter_cycles` = ceil, padding slots skipped). Then any filter count works, at the cost
   of computing and sending the padding slots.

Recommendation: 1 now, then 2 (it also saves cycles and bandwidth, the goal of the fork), 3 only for the remaining
counts.

## 7. Direction 1 applied: `check_full_passes` (approved 2026-11-05, Python only)

`src/open_eye/layer_parameters.py::check_full_passes(layer_params)` raises `NotImplementedError` ("N filters fill P weight
pass(es) x S psums per PE x K kernel(s) per calculation = M filter slots ... (bug #40)") when `needed_wght_cycles x
used_psum_per_PE x different_kernels_per_calculation != filters`; `ConvMapper` calls it right after `check_wght_sets`.
It changes no stream.

* The condition covers one-pass layers too: with two kernels per calculation an odd filter count leaves a padding
  slot (8 x 4 x 1 -> 5: 2 x 3 = 6 slots, 8 x 4 x 1 -> 7: 8 slots). Such layers did not run before either: the
  testbench reference generator fails on them before the simulation starts (`make_ref`: `KeyError` from its worker;
  8 x 4 x 2 -> 6, 2 x 3 slots with no padding, fails the same way, so the reference's limit is odd psum counts per PE,
  not #40; not investigated further).
* Tests (`test/test_channel_pad.py`): an uneven last pass is refused (24 filters in 2 x 16 slots), 30 working layers
  (8 x 8 and 28 x 28, 1 / 2 / 4 / 8 / 32 channels, 16 / 32 / 64 filters) pass, 28 x 28 x 1 / x 2 -> 24 are refused,
  28 x 28 x 1 -> 48 (3 x 16) passes and 8 x 8 x 1 -> 48 (2 x 16 x 2 = 64 slots) is refused.
* Static scan of every Conv layer of the saved profiles (`2026-11-05_b10db82_hang/scan_guards.py`: Table 3 of the
  paper on 16 platforms, the 12 baseline cases, the four trained activation models): 78 layers, **0 refused** by
  `check_wght_sets` or `check_full_passes`.

* Full RTL regression with the check in place: **189 tests = 185 PASS + 4 xfail (known: `conv3_7x7_c64_f64` random and
  trained, `test_iact_channel_mapping[1-3]` and `[3-3]`), 0 FAIL**, the same as before; the check refuses no layer the
  regression runs.

## 6. For upstream (not reported, the fork does not push upstream)

`b10db82` needs #39 (weight sets), #22 (zero-weight encoding) and #40 for any layer whose filters per calculation
exceed 32 and are not a multiple of 32.
