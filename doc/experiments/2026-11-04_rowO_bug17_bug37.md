## 1. Bug #37: the iact buffer fields were 12 bits

**Cause.** Every `iact_stream_constructor` has an 8,192-word iact layer buffer (`ADDRWIDTH` 13), but the status fields
that address it were 12 bits (`regmap.yaml`), and so were the constructor ports and its address registers
(`wr_addr_*`, `rd_addr_*`). Conv 14 x 14 x 32 -> 32 at CLUSTER_ROWS 1, CLUSTER_COLUMNS 2 writes
`iact_buffer_words_per_write` = 4,096 words per pass: the field delivered 0, the writer stops when its word counter
equals that value (`fsm_cycle == needed_iact_buffer_words_i`), so it stopped at once, nothing was written and every
output was the bias. Verilator had flagged the width mismatches all along (`WIDTHEXPAND ... rd_addr_* generates 12
bits`, `WIDTHTRUNC ... ASSIGNW expects 12 bits`).

An overflow check of every field (`fields.py`, the regmap values of the mappers) also shows fields that overflow
silently in configurations that pass (`needed_x_cls_reg` 4 in 2 bits, `start_param_array` 255 in 4 bits,
`iact_write_inc_1` 10,440 in 12 bits, `psum_pagu_cs_limit_2` 55 in 4 bits): they are unused or work by their truncated
value, so a general "every value must fit" check in `pack_registers` would break working layers. The toolchain check
is therefore specific to the iact buffer.

**Fix** (upstream `9498271` widens the same fields to `BUFFER_WIDTH_IACT + 5 - log2(CLUSTERS)`, the width of its own
constructor address; here the width of `dev`'s constructor address):

| File | Change |
|---|---|
| `hdl/OpenEye_FPGA.v` | `localparam IACT_BUFFER_ADDR_WIDTH = 13` (was the literal `.ADDRWIDTH(13)`); wires `iact_buffer_words_per_write`, `iact_read_inc_0..4`, `iact_write_limit_0`, `iact_write_inc_0..2` that wide (were 12 bits) |
| `hdl/iact_stream_constructor.v` | the matching ports and the address registers `wr_addr_0..2`, `rd_addr_0..4`, `rd_addr_inc_*_next` `ADDRWIDTH` bits (were 12) |
| `test/cocotb_fpga/regmap.yaml` | the 10 fields 12 -> 13 bits; `act_neg_mant`, `quant_clamp_low`, `act_neg_shift`, `act_round` (the last 24 bits of the stream) moved into free bits of words 1, 2, 5, so the stream keeps 28 / 14 / 7 words at DMA 32 / 64 / 128 bit in all 96 configurations CLUSTER_ROWS 1-4 x CLUSTER_COLUMNS 1-4 x DMA x BRANCHES 1-2 (without the move: 34 of them one word more, e.g. 29 words at DMA 32) |
| `src/open_eye/layer_parameters.py` | `IACT_BUFFER_ADDR_WIDTH = 13` and `check_iact_buffer`: a layer that needs more than 8,191 words per pass raises `NotImplementedError` instead of wrapping (called by the conv, dense and pooling mappers, as `check_wght_buffer` for #29) |
| tests | `test_cluster_rows1.py::test_cluster_rows1[conv14_c32_x2]` (the failing layer), `test_wght_buffer.py::test_iact_buffer_check`, `test_int8_clamp.py::test_regmap_field` (`quant_clamp_low` no longer the last field) |

## 2. Bug #17: one input channel wider than one x pass

**Cause.** For one input channel the constructor packed two image rows into every buffer word (row 2k in sub-word 0,
row 2k+1 in sub-word 1, `single_write_row / column / half`), with its own write address computed from row and column
only, and read the pairs back with half-word bookkeeping (`single_read_half`, `single_output_half`, a row-pair step in
`rd_addr_inc_4_next`); `data_pipeline_iact` in every PE resumed every other line at sub-word 1 ("uneven ending"). The
write address ignored the x passes of an image wider than one pass (`iact_x_line_repetitions` > 1), so MNIST Conv1
28 x 28 put the passes over each other and the output rows came out equal in pairs. Since 2026-10-22 the toolchain
padded such a layer to two channels (`channel_pad.py`), which costs a second input channel.

**Fix** (as upstream `36395dd`): no row pairs. A one-channel pixel is a buffer word of its own (the activation in
sub-word 0, the other sub-words 0), written and read by the same address loops as several channels, and the PE takes
sub-word 0 of every word.

| File | Change |
|---|---|
| `hdl/iact_stream_constructor.v` | removed: the row-pair writer (`single_write_*`, `ram_wr_addr_q`, `conv_row_words`), the half-word read state (`single_read_half`, `single_output_half`) and the one-channel terms of `rd_addr_inc_1_next` and `rd_addr_inc_4_next`; the buffer is written at `ram_wr_addr` in every mode, with sub-words 1 ... 7 cleared for one channel. Kept from `dev`: the skip of `NUM_GLB_IACT - 1` words after each read of one channel in `rd_addr_inc_0_next` (upstream drops the whole skip term, which `dev` needs for NUM_GLB_IACT 3) and the one-word-per-clock delivery. `stride_y_i` is unused now (lint waiver) |
| `hdl/data_pipeline_iact.v` | `cycle_counter` restarts after every sub-word when `first_spad_max_i == 1`; the uneven-ending bookkeeping removed (`uneven_ending`, `uneven_ending_storage`, `uneven_counter`, the leftover-byte branch); `iact_x_line_repetitions_i` unused (lint waiver, PE interface unchanged). The upstream commit also moves the `!SPARSITY_EN` clear out of the `compute_i` branch: not taken (unrelated, the default is SPARSITY_EN 1) |
| `src/open_eye/channel_pad.py` | padding off by default (`OPENEYE_PAD_CHANNELS=1` turns it on, for comparisons with the measurements before the fix) |
| Python, not taken | `iact_read_inc_2 = ceil(iact_buffer_words_per_write / diff_iact_layer)` of `36395dd`: equal to `dev`'s formula at NUM_GLB_IACT 1, NUM_GLB_IACT times smaller at NUM_GLB_IACT 3, where `dev`'s value is the one that works with the kept skip term |

## 3. Bug #39 (found here): one input channel with more than 16 filters per calculation

**How it showed.** The first full regression with #17 fixed and the padding off had 10 FAILs, all one-channel 28 x 28
layers with 32 filters: the 8 trained-model tests (iact buffer check after Conv1), `test_random_data[28x28_c1_f32]`
and `test_trained_mnist_conv[conv1]` (both hang at the same cycle), while `test_mnist_conv[conv1]` passed: its
constant weights are the same for every filter and hide which filter's weights are used (as they hid #18).

**Narrowing** (`doc/experiments/2026-10-31_upstream_review/up_run.py`, random data, CR 2 X 4):

| Case | `dev` new | upstream `36395dd` | `dev` `87f9bac` (old RTL) |
|---|---|---|---|
| 28 x 28 x 1 -> 4 / 8 / 16 | PASS | PASS (-> 4) | |
| 28 x 28 x 1 -> 32 | FAIL 16/32 | FAIL 16/32 | |
| 40 x 8 x 1 -> 32 | FAIL 16/32 | | |
| 8 x 4 x 1 -> 32 | PASS | | PASS |
| 8 x 4 x 1 -> 64 | FAIL 32/64 | FAIL 32/64 | FAIL 64/64 |
| 28 x 28 x 2 -> 32, 8 x 4 x 2 -> 64 | PASS | | |

So: one input channel and two or more weight passes (`needed_wght_cycles` >= 2), with or without x passes; old
before the #17 fix, and upstream has it too. MNIST Conv1 never met it because it was padded to two channels.

**Mechanism.** A least-squares fit of the effective kernel of every wrong output map
(`2026-11-04_bug39/fit.py` on the `OPENEYE_DUMP_VERIFY` dump of a failing run) gives exactly the kernel of filter f - 16 for f = 16 ... 31,
with the right bias: the second filter group is computed with the first group's weights. The RTL bookkeeping of the
passes is right (`2026-11-04_bug39/probe39.py`, `run39.py n8f64 8 4 1 64` against `n8c2f64 8 4 2 64`: 8 deliveries, `wght_buffer_rd_addr` 0 ... 23 for pass 0 and 24 ... 47
for pass 1, then back to 0, as with two channels), but the weight stream holds only one pass: `trans_cycles_wght` is
120 DMA words (24 buffer rows) for 8 x 4 x 1 -> 32 and for -> 64, while two channels double it (240 -> 480). In
`LayerParameters`, the branch "more than 16 filters per calculation" sets 16 psums per PE and
`wght_transmissions_pe = ceil(channels / channel_div_trans)`: the number of channel batches, not of filter groups. It
is right by coincidence for two channels (2 filter groups = 2 channels) and for 4 or more channels in the configurations
used; for one channel it is 1, and the second filter group is never sent.

**Fix** (Python, `src/open_eye/layer_parameters.py`): `wght_transmissions_pe = ceil(channels / (used_channels *
kernel_per_pe_cluster)) * ceil(filters / (16 * kernels per calculation))`, one weight set per channel batch and filter
group = `needed_wght_cycles x iact_transmissions_pe`, the sets the RTL reads. Over 315 configurations (8 x 4, 14 x 14,
28 x 28 x 1 ... 64 channels x 4 ... 64 filters at CLUSTER_ROWS 1, 2, 4; `2026-11-04_bug39/wtrans.py`) only the
one-channel layers with more than one weight pass change; every other configuration keeps its parameters, hence its
stream. Tests: `test_channel_pad.py::test_weight_sets_cover_every_pass` (8 cases; with the old formula the 4 one-channel
cases fail), `test_mnist_layers.py::test_random_data[8x4_c1_f64]`.
