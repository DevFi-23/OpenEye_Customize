# 2026-10-28: int8 in the OpenEye datapath - investigation, and the saturation (fused ReLU) fix

Sections 1-5: the investigation (no repository change while it ran). Section 6: the fix approved by the user (RTL:
saturation of the quantizers with a per-layer lower bound), section 7 its verification. Tools in `2026-10-28_int8/`.

## 1. Summary

* The quantizers that turn a layer's psums into the int8 inputs of the next layer **kept the low 8 bits**
  (`quantization_unit.v`, `quantized_value <= prod >>> shift` into 8 bits): 130 became -126, -129 became 127. A
  standard int8 network saturates there. Every existing test passed because neither its data nor its reference ever left
  the int8 range: the reference (`batchnorm_output`) did not saturate either.
* A bit-exact emulator of the trained MNIST int8 TFLite model (`doc/demo_notebooks/mnist_quantized_model.tflite`,
  checked against the TFLite reference kernels: bit-exact on every conv and pooling layer, at most 1 LSB on 5 of
  19,200 Dense outputs) puts numbers on every int8 difference of the hardware (10,000 test images, TFLite 99.23 %):
  the model mapped onto today's hardware with Python only reaches **9.3 %**; with saturation it reaches **99.21-99.25 %**
  when the activations are quantized with zero point 0 (section 3).
* A ReLU right after a Conv/Dense needs no activation hardware: in the quantized domain it is a lower saturation bound
  (section 4). The hardware ReLU block `af_cluster.v` was never usable (not instantiated, two bugs, its mode register
  never written; README 8b #24).
* **Fix (section 6):** the quantizers saturate to `[act_min, 127]`; `act_min` is a per-layer status register
  (`quant_clamp_low` = act_min + 128: 0 is plain int8 saturation, 128 a ReLU with zero point 0). Python sets
  `act_min = 0` for a layer with `activation='relu'` (or an imported layer with `relu=True`), the reference saturates
  the same way. No cycle changes (the register fits into the last status word).
* Found on the way: **bug #29**, a Dense layer with K = 3136 inputs and 32 or more outputs computes wrong in RTL
  (K <= 2560, or 16 outputs, are right): it blocks the 3136 -> 64 layer of the trained model.

## 2. The int8 path before the fix

| Part | What it does | Note |
|---|---|---|
| PE multiplier | signed int8 x signed int8, accumulated into the psum (`DATA_PSUM_BITWIDTH`, default 20 bit) | as int8 inference needs |
| PE zero skipping | iact words with value 0 are compressed away (iact SPad overhead) | only a *raw* 0 is skipped |
| bias | loaded into the psum before accumulation (GET_BIAS) | |
| quantizer (`psum_pipeline` -> 8 x `quantization_unit`) | `low8( floor(mant * (psum + offset) / 2^shift) )` | **no saturation** |
| `mant` | 25-bit field of the quant stream, but `OpenEye_FPGA.v:1350` slices it with `+:OFFSET_WIDTH` (8 bits) | effective 8-bit multiplier (0..255); the exponent slice has the same copy-paste (8 bits read into a 7-bit wire: harmless) |
| `offset` | 8 bit, added before the multiplication; Python always sends 0 | cannot carry an output zero point (zp/M is 12,797 ... 673,018 for the trained model) |
| per-filter parameters | `quant_mant[current_filter]`, `current_filter` never increments (bug #12) | filter 0's multiplier for all |
| padding | the iact converter pads with raw 0 | = real 0 only with zero point 0 |
| last layer | psums are sent out raw (`PSUM_SEND_RESULTS`) | the host requantizes |
| Python model flow | weights `floor(127 * w_float)`, bias test patterns, quantize [1, 7] (conv) / [1, 9] (Dense), offset 0; the importers' `qf`/`zp`/`relu` are not used; the TFLite hook loads conv weights only | no real int8 quantization |
| Python reference | `floor(mant * x / 2^shift)` per filter (Dense: shift of filter 0, no `mant`) | consistent with the hardware, not int8 inference |
| conv -> Dense order | the hardware flattens in blocks of 4 channels: `pos = f%4 + 4x + 4X·y + 4XY·floor(f/4)` | a real model's first Dense weights have to be permuted (TFLite flattens NHWC) |

## 3. Emulator: what each difference costs (10,000 MNIST test images)

`emu.py` computes the model the TFLite way (`tflite_exact`: zero points, per-channel multipliers, TFLite rounding,
saturation, padding with the input zero point) and the way the hardware does (`hardware`: raw accumulation, zero points
folded into the bias by Python, `mant`/`shift` with a mantissa width, floor, wrap or clamp, bug #12, padding raw 0 or
zp, psum 20/32 bit, asymmetric (TFLite, zp -128) or symmetric (zp 0) activations). `validate.py` checks the first
against the TFLite interpreter with reference kernels.

| Variant | Accuracy | max abs psum per layer |
|---|---:|---|
| TFLite int8 (interpreter / emulator) | **99.23 %** | |
| H0 trained model on today's hardware, Python-only mapping (zp folded into bias), psum 20 bit | **9.33 %** | 1.0 M, 10.9 M (wraps) |
| H1 same, psum 32 bit | 9.55 % | |
| H2 + saturation | 97.58 % | |
| H3/H4 + per-filter multiplier (#12), + 25-bit mantissa | 96.3 % | |
| H5 + padding with the input zero point | 99.24 % | up to 1.06 M (needs 22 bit) |
| H6 + rounding term in the bias | 99.22 % | |
| H6' as H6 with 8-bit mantissa / H6'' as H6 with padding 0 | 99.23 % / 96.48 % | |
| H7 asymmetric, saturation, padding zp, #12 not fixed, 8-bit mantissa, psum 32 | 99.20 % | |
| H8 asymmetric as H6 but psum 20 bit | **35.03 %** | (wraps) |
| **S5 symmetric (zp 0), saturation with ReLU bound 0, #12 not fixed, 8-bit mantissa, psum 20** | **99.21 %** | 365,571 (fits 20 bit) |
| S1/S2 symmetric, per-filter, 25-bit mantissa, psum 32 / 20 | 99.25 % / 99.25 % | |
| S7 symmetric, per-filter, 8-bit mantissa, psum 20, plain floor | 99.25 % | |
| S4 symmetric, no saturation | 9.33 % | |

Conclusions: saturation decides everything (9 % -> 99 %). With symmetric activations nothing else is needed for this
model (20-bit psum is enough, padding with 0 is right, no input-zero-point correction); bug #12 and the mantissa slice
cost 0.04 points here but are needed for bit-exact agreement and other models. Asymmetric activations (TFLite's zp
-128) additionally need a 32-bit psum and padding with the zero point (RTL), and they lose the zero skipping: after
each ReLU 63-83 % of this model's activations are the real zero (`sparsity.py`), a raw 0 only with zero point 0.

## 4. Fused ReLU without activation hardware

TFLite converts `y = max(0, conv(x) + b)` into one CONV_2D with `fused_activation_function = RELU`; its int8 kernels
implement the activation only as the output clamp: `q = clamp(zp_out + requant(acc), act_min, act_max)` with
`act_min = max(-128, zp_out)` for RELU (`act_max = min(127, zp_out + round(6/s_out))` for RELU6). The requantization is
monotonic (M > 0), so `quant(ReLU(y)) = max(quant(y), quant(0)) = max(q, zp_out)`: a ReLU is the lower saturation bound
at the quantized real zero. The converter calibrates post-ReLU tensors to [0, max], which gives `zp_out = -128`, and
then the ReLU bound is the int8 minimum: every ReLU layer of the trained model has `zp_out = -128`.

For a Keras model quantized by this project's Python (zero point 0): `act_min = 0` for a Conv/Dense with
`activation='relu'` (or followed directly by a ReLU layer), -128 otherwise. Max pooling after a ReLU commutes with it.
Activations that are not a clamp (leaky ReLU, sigmoid, tanh, GELU) still need extra hardware.

## 5. Where the fix goes

The quantizer runs once per output on the final sum, so it is the right place for the activation (the old
`af_cluster` sat on the psum path, where values can be partial sums). The saturation costs two comparators and a
multiplexer per quantizer lane; the bound is a per-layer register.

## 6. The fix (2026-10-28, approved by the user)

| File | Change |
|---|---|
| `hdl/quantization_unit.v` | input `act_min` (signed, OUT_WIDTH bits); stage 3 computes `prod >>> shift` at full width and writes `127` if it is above, `act_min` if it is below `act_min`, else its low 8 bits. Latency unchanged (3 cycles), so the write-back timing is untouched |
| `hdl/psum_pipeline.v` | input `quant_clamp_low` (8 bit); `act_min = quant_clamp_low ^ 8'h80` (subtracting 128 = flipping the top bit) to all 8 quantizers |
| `hdl/OpenEye_FPGA.v` | wire `quant_clamp_low` from `dma_storage` to `psum_pipeline` |
| `test/cocotb_fpga/regmap.yaml` | status register `quant_clamp_low` (8 bit) at the end: it fits into the last status word, the word count stays 14 (64-bit DMA) / 28 (32-bit), so no cycle changes. Encoding act_min + 128 keeps the default 0 at plain int8 saturation for any mapper that does not send it |
| `src/open_eye/layer_parameters.py` | `activation_min(layer)`; `LayerParameters.act_min` (-128 or 0) for Conv and Dense; Dense honours `quantization_factor` like Conv |
| `src/open_eye/conv_mapper.py`, `dense_mapper.py` | send `quant_clamp_low = act_min + 128` |
| `src/open_eye/simple_layer_operations.py` | reference saturates to `[act_min, 127]`; Dense branch multiplies by filter 0's `mant` as the hardware does (no change for `mant = 1`) |
| `src/open_eye/data_create.py` | suffix `_RELU` for any model case (ReLU on every Conv/Dense but the last); test hook `OPENEYE_QUANT_SHIFT` (multiplier 1 and the given shift for every Conv/Dense, so outputs leave int8) |
| `test/cocotb_quantization/` (new) | testbench of `quantization_unit` against a Python model: random and boundary inputs, act_min -128 / 0 / -17 / 5, psum 20 and 32 bit |
| `test/cocotb_fpga/test_int8_clamp.py` (new) | 9 RTL tests: saturation, ReLU, both; conv stacks (4 / 16 channels), conv -> pool -> conv, Dense chain, MLP, `NUM_GLB_PSUM=2`, the paper's network with ReLU |
| `test/test_int8_clamp.py` (new) | `activation_min`, reference saturation (conv, Dense), register position |

Not part of this change: bug #12, the mantissa slice, a Python int8 (PTQ) flow for trained models, bug #29.

## 8. Bug #29 (new): Dense with K = 3136 and 32+ outputs

Found while checking whether the trained model's 3136 -> 64 Dense runs: Dense chains through RTL (random data,
`run_dense.py`): 3136 -> 64 -> 10 and 3136 -> 32 -> 10 fail at the iact check after the first Dense and in the final
result; 2560 -> 32, 2048 -> 32, 1024 -> 64, 512 -> 64, 256 -> 64, 3136 -> 16, 3136 -> 10 pass. Not investigated (a
limit between K = 2560 and 3136 that depends on the output count; possibly the bug #19b family).
