# 2026-11-03: why the three CLUSTER_ROWS = 1 configurations of Table 3 fail (investigation, no RTL change)

Table 3 of the paper (`doc/perf/paper_table3_2026-11-02.md`) runs the network of its Table 2 on 16 configurations; 13 pass.
The three that fail all have one cluster row:

| Configuration | Status (`status.json`) | Bugs (this investigation) |
|---|---|---|
| CR 1 X 4 Y 3 | FAIL: iact check after L5, result | **#29** weight staging buffer overflows (Dense 1568 -> 32) |
| CR 1 X 2 Y 4 | FAIL: iact checks after L3, L4, L5, result | **#28** psum collection starts before the odd PE columns are ready (conv), **#36** the final Dense read-out drops cluster column 1 |
| CR 1 X 2 Y 3 | FAIL: iact checks after L3, L4, L5, result | **#29 + #28 + #36** |

Three separate RTL bugs, each confined to one place. The earlier notes were partly wrong: the CR 1 X 4 Y 3 failure was
attributed to #19b (it is #29), and #28 mixed the conv bug with an unrelated field overflow (#37 below). All three are in
upstream `93f0e82` unchanged. Nothing in the repository was changed; the scripts are in `2026-11-03_table3_cr1/`.

## Bug #29: the weight staging buffer overflows (Dense with many K passes)

**Where:** `hdl/OpenEye_FPGA.v`, `GET_WGHT`: every `WGHT_ONE_WORD_ALL_RAM` DMA words make one row of the weight staging
buffer (`RAM_SP wght_buffer`, `AddrWidth = BUFFER_WIDTH_WGHT` = 12, 4,096 rows); the write pointer `wght_buffer_wr_addr`
is 12 bit and wraps silently. Neither the RTL nor the toolchain checks the size.

**Why it fails:** a row holds `2 x CLUSTERS x NUM_GLB_WGHT` weights (12 at CR 1 Y 3, 3 DMA words). A Dense layer stores
the weights of all its K passes at once: about `K_padded x N / (2 x CLUSTERS x NUM_GLB_WGHT)` rows. Dense 1568 -> 32 at
CR 1 Y 3: 44 K passes of 36 inputs x 96 rows = **4,224 rows**: rows 4,096 ... 4,223 overwrite rows 0 ... 127, the
weights of the first 48 or so inputs; the reads wrap the same way, so the last passes read their own weights and the first
passes read the last ones. All 32 outputs are off by a little.

| Rows of the Dense 1568 -> 32 (load_wght words / words per row) | Y 3 | Y 4 |
|---|---:|---:|
| CR 1 | **4,224** (X 2 and X 4) | 3,168 |
| CR 2 | 2,112 | 1,632 |
| CR 4, CR 8 | 1,056 / 576 | 864 / 400 |

Only CR 1 Y 3 exceeds 4,096 (every conv layer of the network stays below 1,536 rows).

| Check | Result |
|---|---|
| Write-pointer monitor (`T3_WBUF`): D_1512_32 / D_1520_32 / D_1568_32 at CR 1 X 4 Y 3 | 4,032 rows, 0 wraps, **PASS** / 4,128 rows, 1 wrap, **FAIL** 32/32 / 4,224 rows, 1 wrap, **FAIL** 32/32 |
| D_1568_32 at Y 4 (3,168 rows), D_1568_16 (2,112), D_1296_32 (3,456) | PASS |
| D_1568_32 with inputs 0 ... 71 set to 0 (`OPENEYE_ZERO_BLOCK=k:0:72`, the overwritten weights multiply zeros) / inputs 720 ... 791 set to 0 | **PASS** / FAIL |
| `BUFFER_WIDTH_WGHT=13` (8,192 rows): D_1568_32; the whole network CR 1 X 4 Y 3 | PASS; **PASS, all 7 layers**, 133,190 cycles (baseline 133,193) |
| Bug #29 as found on 2026-10-28: Dense 3136 -> 32 at the MNIST platform (CR 2 X 4 Y 3, QUANT_AMOUNT 64) / the same with `BUFFER_WIDTH_WGHT=13` / Dense 2560 -> 32 | 4,224 rows, 1 wrap, **FAIL** 32/32 / 4,224 rows, 0 wraps, **PASS** / 3,456 rows, PASS: the same bug (also explains the passing 3136 -> 16 = 2,112 rows and 3136 -> 10; 3136 -> 64 needs 8,448 rows) |

Bug #19b (N = 32, K >= 508 at NUM_GLB_IACT = 3, `2026-10-21_bug19_dense_k512.md`) is **not** this one: there the weight
buffer read pointer stopped at 768 rows and never wrapped. It stays open and has nothing to do with Table 3.

**Fix directions** (not applied):
1. Toolchain check (Python, recommended in any case): rows = `ceil(load_wght words / WGHT_ONE_WORD_ALL_RAM)` <=
   `2^BUFFER_WIDTH_WGHT`, else refuse the layer with a clear message (as `check_rtl_activation`), instead of a silently
   wrong result.
2. `BUFFER_WIDTH_WGHT = 13` (a build parameter, no logic change; checked above): the default synthesized configuration
   (CR 2 X 4 Y 3, 288-bit rows) would need 4 more URAM (8 -> 12 of 96), to be confirmed by Vivado; cycles unchanged.
   Dense 3136 -> 64 (8,448 rows at CR 2) would still need 14 bit.
3. Long term (RTL): load the weights of a Dense per group of K passes instead of all at once.

## Bug #28: at CLUSTER_ROWS = 1 the psum collection starts before the odd PE columns are ready (conv)

**Where:** `hdl/psum_pipeline.v`, the generate block that builds `chain_ready_terms` -> `all_psum_ready` ->
`results_ready_calc`. It loops over GLB **pairs** (`rr_g < (NUM_GLB_PSUM+1)/2`) and reads `psum_ready_o_reg[GLB]` with
`GLB = ... + rr_g*2`, i.e. only the even GLB of each pair. Its own comment says that at `CLUSTER_ROWS == 1` every PE
column starts a chain, yet the odd columns (column 1 of each cluster at X = 2) are never checked.

**Why it fails:** `CALCULATE_PSUM` starts the collection while an odd column is still computing. The PE rows of a column
then hand their psums up on a fixed schedule, 3 cycles apart (row 2, row 1, row 0). If the late column finishes 3 or
more cycles after the start, its row 1 starts together with its row 2 instead of 3 cycles later and does not add row 2's
psum: one output pixel is wrong in every filter. At X = 2 column 1 of cluster 1 computes x = 4p + 3, the last pixel of a
4-pixel x pass, hence errors at x = 3 and 7. A PE's compute time depends on the number of non-zero activations (zero
skipping), so whether a column lags depends on the data: the error moves with the seed, and a single conv with random
data usually passes.

| Step | Result |
|---|---|
| First 3 layers of the network (conv2 read out), CR 1 X 2, seeds 1 / 2 / 3 | wrong pixels (x, y) = (7, 1) / (3, 7) / (3, 1), (3, 4), (3, 9), all 32 filters each; Y 4: (7, 1); CR 1 X 4: PASS |
| The dumped conv2 data in a single conv (`T3_INJECT`) | the same pixels wrong (CR 1 X 2), PASS at CR 1 X 4 and CR 2 X 2: the conv computation, not the pooling or earlier layers |
| Structured hypotheses (`analyze_px*.py`: a wrong input position / row / column / channel group, a partial sum of another pixel) | none fits exactly |
| Zeros (`T3_NOZERO_IACT`, `T3_SET`) | all zero activations -> 1: PASS; zero weights -> 1: FAIL; only channel group 8-11 matters, also zeros outside the pixel's window (x = 3 ... 5): a timing effect |
| Per-PE streams of a failing and a passing run (one zero at (8, 4, 0) set to 1, outside the window of (7, 1)) | PE cluster 1, column 1 at step (y = 1, x pass 1) receives the same iact words in both runs but outputs different psums: state carried in, not data |
| Its iact SPad / state (`T3_PESPAD`) | the PE enters `SEND_PSUM` 7 cycles earlier in the failing run |
| PE states (`TRACE_ALL_PE`) | the collection starts while cluster 1 column 1 row 2 is still computing (state 6, `pe_rdy_out=01`); that PE then sends 3 cycles late, and row 1 above it starts at the same time instead of 3 cycles after it |
| Ready bits at every collection start (`T3_START`) | seeds 1 / 2 / 3: 36 / 42 / 68 of 448 starts with an odd GLB not ready (`0111` at the failing pass 43 of seed 1); CR 1 X 4 and CR 2 X 2: 0 |
| Emulated fix (`T3_FIXREADY`: `all_psum_ready` forced to the AND of all four ready bits, simulation only) | the 4 failing data sets (seeds 1, 2, 3; Y 4) **PASS**; the network at CR 1 X 2 Y 3 / Y 4 passes every buffer check (L0-L5), only the final Dense still differs (bug #36) |
| Cycles of the emulated fix | CR 1 X 4 Y 4: 0 change; CR 1 X 2: +-16 cycles (<= 0.01 %, the later layers now compute on right data) |

**Fix direction** (RTL, not applied): at `CLUSTER_ROWS == 1` both GLBs of a pair count:

```verilog
if ((CLUSTER_ROWS == 1) && (rr_g*2 + 1 < NUM_GLB_PSUM)) begin : gen_pair
  assign chain_ready_terms[TERM] = psum_ready_o_reg[GLB] & psum_ready_o_reg[GLB+1];
end else begin : gen_even
  assign chain_ready_terms[TERM] = psum_ready_o_reg[GLB] | not_chain_start;
end
```

CR >= 2 keeps the same circuit (every baseline case is CR 2). `chain_enable_terms` (`all_psum_enable`,
`PSUM_GET_RESULTS`) has the same pair structure; emulating its fix too (`T3_FIXENABLE`) changed nothing, so it is not needed
for any failure found.

## Bug #36: the final Dense read-out drops cluster column 1 (CR 1 X 2)

**Where:** `hdl/psum_pipeline.v`, `psum_readout_src` and `psum_buffer_data_temp_reg`, both `TRANS_BITWIDTH_PSUM x CLUSTERS
x NUM_GLB_PSUM` bits wide: **80 bits** at CR 1 X 2. The read-out of a fully connected layer puts cluster column cc's psum
at bit `cc x DMA_BITWIDTH`; for cc = 1 that needs bits 64 ... 83, the guard
`cc_fc*DMA_BITWIDTH + TRANS_BITWIDTH_PSUM <= TRANS_BITWIDTH_PSUM*CLUSTERS*NUM_GLB_PSUM` (84 <= 80) is false and the value
is dropped: those outputs read 0. At CR 1 X 4 and CR 2 the registers are 160 bits wide.

| Check | Result |
|---|---|
| D_32_10 (10 outputs: cluster column 0 holds 0 ... 5, column 1 holds 6 ... 9) | CR 1 X 2: **f 6 ... 9 = 0**; CR 1 X 4, CR 2 X 2: PASS; the two emulated fixes of #28 change nothing |
| D_32_6, D_32_7 at CR 1 X 2 | the outputs on cluster column 1 read 0 (no fixed N threshold) |
| Capture trace in `PSUM_GET_RESULTS` (`T3_CAPTURE`), D_32_10 and the whole network at CR 1 X 2 Y 4 | the right values (e.g. -2995, -3141, 2047, 939 = reference f 6 ... 9) are written into cluster 1's buffer; only the read-out loses them |

**Fix direction** (RTL, not applied): both registers `READOUT_WIDTH = max(TRANS_BITWIDTH_PSUM*CLUSTERS*NUM_GLB_PSUM,
CLUSTER_COLUMNS*DMA_BITWIDTH)` bits, `psum_readout_src` = `psum_buffer_data_r` zero-extended. The conv read-out (packed
path) is unchanged; about +48 FF at CR 1 X 2 only, same cycles. Cannot be emulated without editing the RTL.

## Side finding #37: a conv whose iact write stride is 4,096 (CR 1 X 2, 14 x 14 x 32)

A single conv 14 x 14 x 32 -> 32 at CR 1 X 2 outputs the bias everywhere (`verify_conv_output.py`: every value 1). The
layer needs `iact_buffer_words_per_write` = `iact_write_inc_2` = 4,096, which does not fit their 12-bit fields of
`regmap.yaml` (0 arrives). 24 and 28 channels (3,072 / 3,584) pass, 16 too. Not part of Table 3 (conv2 has 16 channels).
Upstream `655a2ae` makes these fields `BUFFER_WIDTH_IACT` bits wide, still 12 for a 4,096-word iact buffer. Fix direction:
one more bit for the field (and the RTL wire), or refuse the layer in the toolchain.

## Upstream

`upstream/main` is still `93f0e82` (2026-10-29); no branch has a newer commit. Its code has all three bugs: the weight
buffer is `BUFFER_WIDTH_WGHT` = 12 with no check (#29), `results_ready` ANDs `psum_ready_o_reg[... + g_psum*2]` only (#28,
the same loop before our bug #14 rewrite), and `psum_readout_src` has the same width (#36). `655a2ae` ("Fixed adresses
and ranges for bigger Nets and input activations", the recent "larger buffers" commit) widens counters and fields
(`trans_cycles_*` 24 bit, `iact_read/write_limit_*` 12-18 bit, psum loop limits 12 bit, iact increments
`BUFFER_WIDTH_IACT` bit) but does not touch the weight buffer, the ready aggregation or the read-out: it fixes none of
#28, #29, #36, and not #37 with a 12-bit iact buffer. The upstream run of 2026-10-31 (`2026-10-31_upstream_review.md`)
already showed #28 and #29 failing there.
