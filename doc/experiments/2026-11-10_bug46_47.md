# 2026-11-10: bugs #46, #47 (and #48) of the dense mode (`SPARSITY_EN=0`): cause, upstream, fixes

**Applied on 2026-11-10 after approval: section 6** (the RTL fix of #46 / #47 as proposed, a check for #48, tests).
Sections 1-5 are the investigation, made before anything was changed. The causes were found with a PE monitor
(`2026-11-10_bug46_47/probe47.py`, through `run47.py`, on the fork's own flow, 2 x 2 clusters, `NUM_GLB_PSUM` 4, random
data, seed 1); the proposed patch (`2026-11-10_bug46_47/proposal_46_47.patch`) was only tried in a temporary copy of
`dev` (section 4).

## 1. Bug #47: an all-zero weight word in a dense convolution

**Trace** (8x4x16 -> 16, PE cluster (0,0), column 0, row 2; configuration C0 = 4 channels, M0 = 8 filters, 3 iacts per
channel): the PE must hold 48 weight words (4 channels x 3 kernel columns x 8 filters / 2 MACs). Words 0..35 are written;
the 37th word on the port is `0x0000` (two zero weights: the random test weights of the fork are small, |w| <= 19 here,
2.8 % zeros); after it the next 12 words are written at addresses 0..11 again, and the PE starts with
`second_spad_words_wght` = 12 instead of 48.

**Cause:** `hdl/data_pipeline_wght.v` stores a word only if it is non-zero or `raw_mode_i` is set (lines 511, 520, 574),
the sparse convention (a sparse stream never carries an all-zero word). Otherwise the cycle is treated like a gap:
the word is dropped and `second_spad_addr_o <= 0`. `raw_mode_i` is set only for fully connected and GEMM layers
(`OpenEye_FPGA.v`: `.raw_wght_i(fully_connected_layer | gemm_mode)`), never for a dense convolution.

**Consequence:** with 12 words the dense FSM wraps `wght_data_vec` every 3 iacts; each wrap raises `mux_iact_ready`,
which advances the iact address a second time (`PE.v` dense `CALCULATING`), so the PE reads iact addresses 12..14 that
were never written: X. Both MAC lanes of that PE turn X; in the output every even filter is X, the odd ones are right.

**Not specific to 16 channels:** it needs a weight block with two zero weights in one word. 8x4x16 -> 16 with seed 2 has
none and passes; the trained MNIST net (1-5 % zero weights) has them (its Conv2 / Conv3 / Dense were wrong in dense).

**Check without changing the RTL:** holding `OpenEye_Parallel.raw_wght_i_reg` at 1 in the simulation (cocotb `Force`,
`P47_FORCE_RAW=1`): 8x4x16 -> 16 seed 1 **PASS**.

**Upstream:** the same RTL (`data_pipeline_wght.v` identical, raw mode only for FC / GEMM) in `b1e02a0` and `9a742fb`;
its Python drops all-zero words of a convolution sent in one weight transmission
(`wght_stream_mapper.py`: `if (temp_trans != 0) or not self.SKIP_ZERO_WORDS or (needed_wght_transmissions > 1)`), so
the PE gets one word less and every later weight shifts: the same bug, hidden in its tests because its random weights
(seeds 1-4 tried on 8x4x16 -> 16, both trees) have no zero pair. Upstream already solved the same problem on the iact
side: `data_pipeline_iact.v` stores every word in dense mode, `... | (!SPARSITY_EN)` in the store conditions
(DenLeb, `9c143b7` "Added PE Support for Sparse and SISD efficiently" 2026-07-22, `1a8864d` "Fixed Dense Stream"
2026-08-06). The weight pipeline did not get that term.

**Proposal (upstream's pattern, 3 lines):** in `data_pipeline_wght.v` treat dense hardware like raw mode, i.e. replace
`raw_mode_i` by `raw_mode_i | !SPARSITY_EN` in the three store / advance conditions. `SPARSITY_EN` is a parameter: the
sparse build is unchanged gate for gate. The Python side is already done in the working tree (dense keeps zero words,
`wght_stream_mapper.py`, 2026-11-09). Alternative, not recommended: `.raw_wght_i(fully_connected_layer | gemm_mode |
!SPARSITY_EN)` in `OpenEye_FPGA.v` (1 line, same effect on the FPGA top, but the PE alone, e.g. in the PE / cluster
testbenches, would still be wrong).

## 2. Bug #46: psum read-after-write in the dense FSM

**Measured** (raw mode forced so that #47 does not interfere; 8x4x4 -> F): `used_psum_per_PE` (= M0, filters per PE) 2, 3,
4 wrong; 6, 8 right. Upstream `9a742fb` also fails 8x4x4 -> 4 (as `b1e02a0`).

**Trace** (8x4x4 -> 4, M0 = 4): weights and iacts are read in the right order and aligned (24 weight words, filter pairs
0-1 / 2-3 for every iact). With `PARALLEL_MACS` 2 a filter pair's psum address comes back every M0 / 2 cycles; with
M0 <= 4 that is within 2 cycles, while the previous sum for that address is still in the write pipeline
(`psum_spad_addr_w == psum_spad_addr_r`).

**Cause:** for exactly this case `PE.v` suppresses the SPad write (`psum_data_SPad_en_w_i`) and expects the FSM to
forward the adder output (`reuse_psum_spad`, `reused_data`). The sparse FSM's `CALCULATING` does it (Hendrik Woehrle,
`4e8402c` 2026-09-06, loop fixed in `e2eab3c`; its comment: "It only shows up once a weight row is short enough for the
same filter to recur within the two-cycle write pipeline"). The dense FSM (`c8ec883` "refactorig for dense/sparse
modes", 2026-02-19, before that fix) sets `reuse_psum_spad <= 0` in every `CALCULATING` cycle and has the forwarding
only in `WAIT_TO_SEND_PSUM`, so the accumulation is lost.

**Upstream:** the dense FSM is identical in `b1e02a0` and `9a742fb`; no later commit touches `PE.v` or
`data_pipeline_wght.v`. Upstream does not see it in its own configuration (1 x 1 cluster, `PARALLEL_MACS` 1: a psum
address recurs only after M0 cycles).

**Second cause, M0 <= `PARALLEL_MACS`** (found while trying the fix below; 8x4x4 -> 2, M0 = 2): `wght_filter` stays 0
(the filter loop restarts every cycle), so the base-address reset `if (wght_filter == PARALLEL_MACS)` never fires and the
psum address walks 0,1 -> 2,3 -> ... -> 24,25 over the pass instead of staying at 0,1 (`TRACE_PE_PSUM`). The sparse FSM
does not have this path. Upstream's configuration (`PARALLEL_MACS` 1) has the same gap for one filter per PE.

**Proposal (upstream's own fix plus one condition, about 23 lines in `PE.v`, dense FSM only):**
(a) copy the forwarding block of the sparse `CALCULATING` (same lane and, with `SERIAL = 0`, cross lane) into the dense
`CALCULATING`, after its defaults; (b) reset the psum base address also when the PE has at most `PARALLEL_MACS`
filters: `if ((wght_filter == PARALLEL_MACS) | (filters_reg_M0 <= PARALLEL_MACS))`. Interim alternative without RTL:
refuse a dense convolution with `used_psum_per_PE <= 4` and `PARALLEL_MACS = 2` in `LayerParameters` (like the group A
checks).

## 5. New bug #48: odd number of filters per PE in dense mode

8x4x4 -> 6 gives M0 = 3. The dense FSM uses `ceil(M0 / 2)` = 2 weight words per iact (filters 0-1, 2-padding): 4
channels x 3 x 2 = 24 words per pass, but the Python block is `ceil(used_wght_per_PE / 2)` = 18 words (no padding slot
per iact), so the weights shift and `wght_data_vec` wraps early. In sparse mode the same layer is refused by the Python
encoder (`ValueError: encoded columns need 24 words, the PE block has 18`, bug #22's column rule); in dense it is
silently wrong. M0 is odd for odd filter counts (1, 3, 5, ...) and for some narrow inputs (8 wide, 6 filters). Proposal
(Python only): first a check in `LayerParameters` that refuses an odd `used_psum_per_PE` with `PARALLEL_MACS = 2` in
dense mode; later the padding slot per iact column in the dense layout (each column `ceil(M0 / 2)` words, as
`encode_columns` does) with `used_wght_per_PE` and the weight transfer count rounded up to match.

## 6. Applied (2026-11-10, approved)

* RTL: `proposal_46_47.patch` applied as it is (`hdl/data_pipeline_wght.v` 3 lines, `hdl/PE.v` 1 changed + 22 added
  lines, dense FSM only).
* Python: `check_dense_wght_slots` (`layer_parameters.py`, called by `conv_mapper.py` after `check_full_passes`) refuses
  a convolution whose weight block the dense PE would read with another layout (#48: `used_iact_per_PE x ceil(M0 / 2)`
  words read against `ceil(used_wght_per_PE / 2)` sent), dense hardware only, `NotImplementedError` naming bug #48
  (`OPENEYE_ALLOW_UNSUPPORTED=1`: warning). On every configuration of sections 4 and the MNIST layers it refuses exactly
  the odd filter counts per PE (8 x 4 x 4 -> 3, 6, 10).
* Tests: `test/cocotb_fpga/test_dense_mode.py` (10: the dense cases of section 4 with the investigation's data, and the
  trained MNIST net), added to `2026-11-07_bug41_stride/regression.sh`; `test/test_model_guards.py` +8 (#48).
