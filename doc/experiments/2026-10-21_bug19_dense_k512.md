# Investigation 2026-10-21: bug #19, Dense layers with more than 512 inputs are wrong

No RTL and no repository code was changed. Tools: a scratch runner around `test_gemm_layer.test_gemm_layer`
(`2026-10-21_bug19/dense_k.py`: one Dense layer, K inputs, N outputs, row stationary, 2x2 clusters, `NUM_GLB_IACT=3`,
`NUM_GLB_PSUM=4`, `NUM_GLB_WGHT=3`, `PARALLEL_MACS=2`, random data, live FC write check off) and cocotb probes that wrap the
unmodified `OpenEye_FPGA_tb` (same folder). RTL = `dev` at `f337693`.

## 1. Where it starts (N = 10 outputs, the MNIST shape)

| K | 64 ... 300 | 504 | 512 | **513** | 514 | 516 | 518 | 520 | 576 | 578 | 784 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| Result | PASS (64, 264, 300; 2026-10-19: 64 ... 512) | PASS | PASS | **FAIL** | FAIL | FAIL | FAIL | FAIL | FAIL | FAIL | FAIL |

One extra activation is enough: K = 513 fails. K = 264 and K = 300 pass although their low 8 bits are non-zero (264 has the same
low byte as 520), which rules out the 8-bit field `iact_converter_params_reg[...][15:8] <= iact_x_add_up`
(`OpenEye_FPGA.v:908`).

The Python mapping is not the limit: `write_dense_layer` gives `used_iact_per_PE = 12` and `diff_iact_layer = 8` for every K from
505 to 576, i.e. 8 K tiles of 72 activations = 576 slots, enough for K = 520.

## 2. What the DUT computes (exact)

`probe_b19.py` dumps the operands the DUT receives (`dram.fmap`, `dram.weights`, `dram.bias`), the reference and the DUT outputs;
`analyze.py` tests hypotheses on the integers:

| Layer | H0: activations with index >= 512 read as 0 | H1: read as x[k-512] | H2-H4: x[k-512] overwritten |
|---|---|---|---|
| K = 520, N = 10 | **10/10 outputs exact** | 0/10 | 0/10 |
| K = 784, N = 10 (Dense of the repository MNIST net) | **10/10 outputs exact** | 0/10 | 0/10 |

Least squares on the positions 512..519 (K = 520) gives the effective activations `[0, 0, 0, 0, 0, 0, 0, 0]` (true:
`[-1, 10, -13, -14, -9, -8, -7, -9]`) with residual 0. So **every activation from index 512 on is replaced by zero**, the other
512 are correct.

## 3. Mechanism (constructor probe)

FC activations travel as pairs; the converter in `OpenEye_FPGA.v` sends one pair per cycle and every `iact_stream_constructor`
stores the pairs of its window into its iact RAM (`WRITE_TO_MEMORY`). The position in the stream is counted by

```verilog
// hdl/iact_stream_constructor.v:214
reg [ 8-1:0] x_pos_in_w_cycle;
...
if (x_pos_in_w_cycle >= x_range_lower_bound) begin                      // x_range_lower_bound is 12 bit
  if (x_pos_in_w_cycle < x_range_lower_bound + iact_values_per_cluster_transmit) begin
    enable_write_to_storage <= 1;
...
x_pos_in_w_cycle <= x_pos_in_w_cycle + 1;
if (x_pos_in_w_cycle == iact_x_add_up + wght_size_x - stride_x_i - 1) begin   // never true for K >= 256 (8-bit counter)
```

`probe_ctor.py`, constructor (0,0) (cluster row 0, windows of 18 pairs every 36 pairs, the last one starting at pair 252):

| Stream position p | `x_pos_in_w_cycle` | window start | written |
|---|---|---|---|
| 252 ... 255 | 252 ... 255 | 252 | yes |
| **256** | **0** (8-bit wrap) | 252 | **no** |
| 257 ... 259 | 1 ... 3 | 252 | no |
| 508 ... 511, 764 ... 767, 1020 ... 1023 | 252 ... 255 again | 252 | yes (zeros of the padded stream) |

The data on `storage_i` arrives two cycles after the decision; at K = 520 it carries the real pairs 256 ... 259
(activations 512 ... 519), which are never written. The counter keeps running for the whole state (1,172 cycles) and passes
252 ... 255 three more times; each time 4 words of the zero padding are written to the next RAM addresses, i.e. exactly where
pairs 256 ... 259 belong. Write counts are identical for K = 512 and K = 520 (142 for row 0, 126 for row 1): the extra pairs
are dropped and their slots hold zeros, which is what section 2 measured. At K = 512 those slots are padding anyway, so the
layer is correct.

The same 8-bit width is used for the window start `x_start` (`iact_stream_constructor.v:158`) and for
`iact_converter_x` / the x field `[31:24]` of the converter parameters (`OpenEye_FPGA.v:840`, `:916`). In these Dense runs the
constructors only received the starts 0 and 18, so they are not involved; they would matter for wider windows (and for
convolutions on images wider than 255 pixels, where `x_pos_in_w_cycle` counts pixels).

## 4. Ruled out

| Candidate | Evidence |
|---|---|
| `PE.v` width of `first_spad_words_wght` (upstream `2bf497d`) | K = 520 fails with the old and the new PE alike |
| 8-bit `iact_x_add_up` field (`OpenEye_FPGA.v:908`) | K = 264 and 300 pass |
| Weight-buffer read pointer (12 bit) | `probe_wbuf.py`: the read pointer stops at 288 (N = 10, K = 512), 768 (N = 32), never wraps |
| Weight address SPad (64 entries) | `first_spad_addr_o` wraps 63 -> 0 in 36 PEs at K = 512 for N = 10, 16, 24, 32 - also in passing runs |
| Not enough K tiles in Python | 8 tiles x 72 = 576 slots for K = 505 ... 576 |

## 5. Next barrier, from code reading (not testable before the fix)

In `CONVERT_IACT` (`OpenEye_FPGA.v:2143-2160`) the converter counts activations in `reg signed [11:0] current_x` and stores a pair
only if `current_x >= 0` (signed). From activation 2048 on the counter reads negative, so a layer with K > 2048 (MNIST FC 3136)
would lose those activations even after the fix of section 3.

## 6. Separate findings (not bug #19)

| # | Condition | Observation | Status |

| 19b | N = 32 and at least 8 K tiles | K = 360, 432, 480, 504 PASS; **K = 508 and 512 FAIL** (all 32 outputs). N = 16 and 24 pass at K = 512. The error is not confined to a few activations (least squares on the last 8/16/24 activations leaves large residuals), so it is on the weight or psum side. For N = 32 the weight data SPad write address reaches 97 (the SPad has 96 words) - also in the passing K = 480/504 runs | root cause not found |
| 21 | N > 32 (two psum transmissions), any K | K = 64: N = 32 PASS, **N = 40 FAIL (outputs 10-39 wrong), N = 48 FAIL (12-47 wrong)**; only the first `used_psum_per_PE` outputs are right | not investigated |

A tested hypothesis that failed: "tiles x psums per PE >= 128" predicted PASS for N = 40 / K = 432 and N = 48 / K = 360; both
fail, now explained by bug #21.

## 7. Proposed fix (not applied, needs approval)

`hdl/iact_stream_constructor.v`: widen `x_pos_in_w_cycle` to 12 bits (the width of `x_range_lower_bound`, `x_pos_inc` and
`iact_x_add_up`) and `x_start` to 12 bits. Then the end-of-row reset `x_pos_in_w_cycle == iact_x_add_up + ...` becomes reachable
for 256 <= K: it now fires after the real data (the FC stream has K/2 pairs, the compare uses K), which only changes the zero
padding written after the data. For K > 2048 also `current_x` (section 5).

Verification plan: the K sweep above (513, 520, 576, 784, with `analyze.py` exact), the 125-test regression with the lock-step
technique for `iact_stream_constructor` where the old and new modules must agree (K < 256 everywhere in the suite), Conv cases,
Vivado.

Without RTL change (Python only): split a Dense layer with K > 512 into chunks of at most 512 inputs, run them as separate layers
and add the partial sums on the host (bias in one chunk only). Costs one extra weight/iact load per chunk.
