No RTL file was changed. Scripts in `2026-11-07_bug41_stride/`: `window_map.py` (which input window each DUT output was
computed on), `dense_run.py` (one Dense layer through `test_gemm_layer`), `scan_guards.py` (static scan of the saved
profiles through the new checks), `regression.sh` (the 189-test RTL regression). Strided runs use
`2026-11-04_bug39/run39.py` (CR 2 x CC 2, NUM_GLB_PSUM 4, NUM_GLB_IACT 1, DMA 64, random data, seed 1, `OPENEYE_DUMP_VERIFY`),

`upstream/main` = `b1e02a0`.

## 1. What the DUT computes with stride 2

Conv 8 x 8 x 4 -> 16, kernel 3, stride 2, default build (`STRIDE_ENABLED=0`): 16 of 16 feature maps wrong, 207 of 256
values. `window_map.py` computes the stride-1 "same" convolution of the integers the DUT received and finds, for every
output position, the window centre whose value equals the DUT's in all 16 filters:

| output (x, y) | reference window centre | DUT window centre |
|---|---|---|
| (0, 0), (0, 1), (0, 2) | (0, 0), (0, 2), (0, 4) | the same: correct |
| (x, y), x = 1..3, y = 0..2 | (2x, 2y) | **(x, 2y)**: x advances by 1 pixel, not 2 |
| (x, 3) | (2x, 6) | **none**: centre (x, 6) without the third kernel row (the taps of input row 7) |

So the y direction is strided (3 of 4 rows), the x direction is not, and the last output row misses its last kernel row.

## 2. Cause: stride is an optional part of the RTL, off by default

* `hdl/OpenEye_FPGA.v:129` `parameter STRIDE_ENABLED = 0`; lines 369-370
  `assign stride_x = STRIDE_ENABLED == 1 ? stride_x_dma : 1;` (same for y); lines 1469-1470 the converter bounds
  `x_bound` / `y_bound` subtract `stride` only when enabled, else 1. `src/open_eye/open_eye_parameters.py` reads
  `STRIDE_ENABLED` from the environment, default 0, and `vh_file_creator.py` writes it into `parameters_FPGA.vh`.
* With 0, `iact_stream_constructor` gets `stride_x_i = 1`: the window of PE column `pec` starts at `pec * stride_x_i`
  (line 332) and the x loop ends at `iact_x_add_up + wght_size_x - stride_x_i - 1` (line 592), i.e. stride 1 in x.
* The y stride does not depend on the parameter: the host programs the read loops with it
  (`layer_parameters.get_pagu_values`: `iact_read_limit_4 = ceil(iact_size_y / strideY) - 1`,
  `iact_read_inc_4 = iact_read_inc_1 * strideY`). Host and RTL disagree, hence the mixed pattern of section 1; the
  missing kernel row of the last output row fits `y_bound = iact_size_y + padding_y - 1` instead of `- stride_y`
  (not traced further).
* History: upstream `2e3b351` (DenLeb, 2026-09-16, "Readded input activation and single layer support for strides")
  added the parameter with default 0 and the stride terms of the constructor and the Python.

**Built with `STRIDE_ENABLED=1`** (`STRIDE_ENABLED=1` in the environment of the run, checked in `parameters_FPGA.vh`;
the toolchain's reference, symmetric padding; `OPENEYE_ALLOW_UNSUPPORTED=1` for the runs made after the checks existed):

| Case (W x H x 4 -> 16, kernel 3) | `STRIDE_ENABLED=0` | `STRIDE_ENABLED=1` |
|---|---|---|
| 8 x 8, stride 1 | PASS, 33,150 ns | PASS, 33,150 ns (identical); 7 x 7 stride 1: values right (#9 padding slot only) |
| stride 2, CR 2 x CC 2, NUM_GLB_PSUM 4, widths 8 (heights 4, 7, 8, 12), 16 (4, 16), 24, 28, 32 (8) | 8 x 8: FAIL, 207 / 256 values | **PASS** (8 x 8: 20,530 ns, 16 x 16: 46,050 ns) |
| stride 2, same platform, widths 4 (height 8), 6 (6, 8), 7 (7, 8), 9 (8, 9), 12 (8, 12) | | **FAIL**, 15-16 of 16 maps |
| stride 2, NUM_GLB_PSUM 2, widths 4, 8 / width 6 (height 8) | | PASS / **FAIL** |

**Bug #41b: with stride enabled the result depends on the input width, not the height** (8 x 12 right, 12 x 8 wrong).
`window_map.py` on 12 x 8: only 224 of the 384 output slots decode, and the values found are correct windows at the
wrong output positions (output (4, 1) holds the window centred at (0, 2), (5, 1) the one at (2, 2)); on 7 x 7 no
position matches any window. So the MACs compute real windows, but the order and number of the outputs of a strided
layer differ from what the host expects (`psum_output_words`, the output order, or the RTL's read-out of the x
passes): not traced further. No simple rule fits all widths (a multiple of 8 does not: 28 is right, 12 wrong).

## 3. Is it a bug or a feature? What the documents say

* Stride is part of the design: `doc/source/architecture/PE_cluster.md` (the Eyeriss v2 row-stationary mapping: "Window
  slides by C0 x U elements (U = stride)", CSC segments of C0 x U), status fields `stride_x_reg` / `stride_y_reg`
  "Convolution strides" of 3 bits, 1-8 (`doc/OpenEye_FPGA_documentation.md`, `doc/source/architecture/configuration.md`,
  `dma_regmap.rst`, `fpga/overview.rst`, `fpga/internals.rst`).
* It was never tested: `doc/source/architecture/sparsity_modes.rst`, "Test Coverage Gaps": "Different stride
  configurations (stride=1, stride=2)" open; the upstream test `test/cocotb_parallel/test_single_layers.py` keeps
  `(2, 2)` in a comment.
* `STRIDE_ENABLED` is listed without a description (`doc/source/verilog/OpenEye_FPGA.rst:129`); no document says that
  the default hardware has no stride.

Verdict: two defects. #41 is a configuration / toolchain bug: the default build has no stride while the toolchain
accepts a strided layer and streams it without a word. #41b is a real bug of the optional stride path: built with it,
stride 2 is right only for some widths (section 2). Neither is a fault of the MAC arithmetic.

**A second, independent mismatch: TensorFlow's "same" with a stride.** The RTL and the testbench reference pad
kernel // 2 on every side (PyTorch `padding=1` semantics: centres 0, 2, 4, 6 for 8 pixels). TensorFlow / Keras "same"
pads `(out - 1) * stride + kernel - size` in total with the odd pixel at the end: 8 pixels, kernel 3, stride 2 give
[0, 1], centres 1, 3, 5, 7. The two agree for odd sizes (7 pixels: [1, 1]) and differ for even ones. The stride-2 runs
above passed against the toolchain's own reference, which is not what the Keras layer computes. `tf_same_pads` and
`test_model_guards.py::test_tf_same_pads_is_tensorflow` check the formula against `tf.nn.conv2d`.

| Case | Result |
|---|---|
| 8 x 8 x 4 -> 16, stride 1 | PASS |

| stride 2, `STRIDE_ENABLED=1` | "values differ, reference file ok": the DMA output stream equals the reference stream, but upstream's testbench decodes the values one row off (decoded y = 1 holds the reference's y = 2, y = 2 and 3 are 0; 252 differences): an upstream testbench defect, the fork's decoder is right |

## 5. Solutions

1. **Done (Python): refuse.** `layer_parameters.check_conv_geometry` (called by `ConvMapper`) refuses every stride above
   1: with `STRIDE_ENABLED=0` as #41, with `STRIDE_ENABLED=1` as #41b. It also refuses a model padding that is not the
   RTL's, including TensorFlow "same" with a stride on even sizes. `OPENEYE_ALLOW_UNSUPPORTED=1` only warns, to rerun
   the cases above.
2. **Next, needs investigation before any hardware change: #41b.** Find why the output order / count of a strided
   layer depends on the width (start from 12 x 8 against 8 x 12 and 16 x 4: `psum_output_words`,
   `iact_x_line_repetitions`, `iact_x_pos_inc`, `x_range_lower_bound` of the constructor, the psum read-out); the
   Python side first (no RTL change), then, if the RTL is at fault, a proposal for approval.
3. **Then (hardware parameter, no RTL code change, needs approval): build with `STRIDE_ENABLED=1`.** Necessary but
   not sufficient (item 2). Stride-1 layers kept their cycle count in the one case measured. Cost (Yosys 0.69,
   `synth_xilinx -family xc7`, `iact_stream_constructor` alone at the baseline platform, stride input free against
   tied to 1): 792 / 717 LUT, 341 / 337 FF, 120 / 103 CARRY4, i.e. +75 LUT, +4 FF, +17 CARRY4 per constructor, about
   +300 LUT for the four (0.5 % of the 59.4k LUT of the Vivado baseline); measure with Vivado and rerun the regression,
   baseline and Table 3 before adopting.
4. **TensorFlow "same" with stride 2 on even sizes, first layer only:** the host can send the input shifted by one
   pixel (drop the first row and column, append a zero row and column); the RTL's windows -1..1, 1..3, ... then cover
   TensorFlow's 0..2, 2..4, ... exactly. A later layer reads the previous layer's write-back on chip and cannot be
   shifted; PyTorch / ONNX models with `padding = kernel // 2` need nothing.
5. Upstream's stride decoding is upstream's (the fork does not push upstream).
